# JSONL worker (experimental)

`opencrowd worker --protocol jsonl --agent-home /path/to/home --demo` runs the existing agent loop with a scripted model and real local file tools. It has no paid execution or local wallet fallback. Ordinary CLI commands keep their existing configuration and provider behavior.

stdin accepts protocol-v1 commands from `@opencrowd/protocol`; stdout emits only validated protocol events. Diagnostics go to stderr. Keep stdin open to submit cancellation while a run is active. Closing stdin drains the active run and exits.

The caller owns command IDs, run IDs, and preferably session IDs. Re-deliver the exact command envelope after a process interruption. Reusing an ID with different contents is rejected. Completed commands are acknowledged without another model/tool execution. Waiting runs resume only when the cause, session, and pending operation match.

`metadata/worker.json` contains the authoritative checkpoint and command acknowledgements. Non-secret configuration and session files live beneath the explicit home. Session paths are recalculated when restoring to another location. Checkpoints are atomically replaced and synced before terminal outcomes. Model requests receive a stable operation ID; a remote payment adapter must use that ID for reconciliation and must never create another authorization for an ambiguous payment.

An interrupted shell action with no recorded result fails for manual reconciliation instead of automatically replaying its side effects. Local file writes are repeatable, and recorded tool results are reused. The supervisor must copy artifacts and the quiescent home before acknowledging the terminal event; it must recover a missed artifact event by listing the checkpointed session files.

For a supervised hosted model, replace `--demo` with `--bridge-socket /absolute/path/to/model.sock`. Exactly one mode is required. The Unix socket accepts a bounded `POST /model` request containing the run, session, stable model-operation ID, messages, and built-in tool definitions. A response is either `{status:"complete",response:{content,toolCalls,finishReason?}}` or `{status:"paused",outcome,operationId,message}`. The supervisor authenticates remote requests and must constrain them to the current run; the worker receives no signing credentials. Interrupted requests pause for payment reconciliation without a provider fallback.

Before each `POST /model` the worker trims the replayed history to 48 KB (`trimHostedMessages`, measured as the JSON byte length of the messages array) so long-running follow-ups do not outgrow the bridge's 64 KB request limit. Every `system` message, the first `user` message, and the last four messages are always sent untouched. Older tool outputs longer than 300 characters are replaced first with `{"truncated":true,"note":...}`; if that is not enough, whole older turns are dropped oldest-first, with an assistant message and its tool results removed together so the model never sees an orphan result; as a last resort the largest remaining non-system message (other than the latest user message) is cut to its last 6000 characters with a `[…trimmed…]` prefix. Trimming is pure and deterministic and does not alter the checkpoint, which keeps the full conversation.

A non-200 bridge response is classified by its JSON body `{error, message?, status?, paid?}`. Only an explicit `paid: false` proves that nothing was charged: the run then finishes with outcome `failed` and `message` (or `The model request was rejected (<error>)`) as the summary, which the host should show to the user. Any other failure — a body without `paid`, `paid: true`, a non-JSON body, a transport error, or the 90-second socket timeout — still pauses the run with `payment_unknown` for reconciliation, exactly as before.

The same socket accepts a bounded `POST /tool` request for supervisor-executed tools (`HOSTED_ONLY_TOOL_NAMES`: `deploy_service` and `request_secret`). The body carries the run, session, tool name, and arguments; for `deploy_service` the worker inlines the entry artifact's source, while `request_secret` forwards its arguments untouched. The response is a plain `{ok, data}` or `{ok:false, error}` tool result. Hosted-only tools are advertised only to hosted models, are refused by the local executor, and are memoized per checkpoint turn like every other tool. A lost tool response is reported to the model as an error rather than treated as a payment, because deployments are idempotent per slug and secret requests are idempotent per name.

`request_secret` takes `name` (`^[A-Z][A-Z0-9_]{1,63}$`), `allowed_hosts` (hostnames the secret may be sent to), and `reason` (one sentence for the user). The supervisor asks the user to add the value to the agent's encrypted vault through the host UI and returns `{status: "requested" | "active", placeholder?}`; the worker and the model never see the value. The hosted system prompt tells the model to request secrets by name this way, never to ask the user to paste a secret into the chat, and to consume them through `deploy_service` `secrets` as `env.NAME`.

`tool.started` events carry a redacted `input` summary produced by `summarizeToolInput` so hosts can show progress without leaking data: `run_shell` → the first 200 characters of the command, `save_file`/`read_file`/`list_files` → the path, `deploy_service` → slug, name and price, `request_secret` → name and allowed hosts, `complete_session` → the first 200 characters of the final message. File contents and secret values are never included; other tools carry no summary.

Tests include a real `SIGKILL` between a completed file tool and the next model response, followed by process restart: the artifact and single user prompt survive, the completed tool is not repeated, and the next model operation keeps its original ID. Hosted subagent checkpointing and production image rollouts remain separate integration gates.
